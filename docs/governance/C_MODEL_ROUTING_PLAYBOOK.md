# C. 模型調度守則（Model Routing Playbook）

> 讀者：未來擔任「主模型」的任何 coding agent（Sonnet / Opus / GPT-5.5 等級皆適用）。
> 目的：決定什麼自己做、什麼派出去、什麼要升級、什麼要停下來。
> 模型名稱一律用抽象等級寫成可抽換格式；實際名稱需依當時環境查得後填入（本 pack 內沒有可用模型清單，不要假設）。

---

## 0. 模型等級定義（抽換表）

| 等級代號 | 定義 | 典型任務 | 環境實名（接手時填入） |
| --- | --- | --- | --- |
| `low-cost` | 最便宜、快速、弱推理 | 批次格式轉換、跑測試回報結果、機械式套用已定義 patch | ＿＿＿ |
| `standard-coding` | 中階主力 coding 模型 | 一般實作、加測試、照 spec 寫 validator 規則 | ＿＿＿ |
| `high-reasoning` | 當前環境最強推理模型 | 架構決策、governance 規則設計、模糊需求拆解 | ＿＿＿ |
| `fresh-context-reviewer` | 與作者不同 context 的任一模型 | read-back、對抗審查、驗收 | ＿＿＿ |
| `second-opinion` | 與主模型不同系的模型（若環境有） | 高風險判斷的第二意見 | ＿＿＿ |

填入實名的方法：查看當前 harness 的可用模型清單（如 Claude Code 的模型設定），把實名寫進本表並 commit。**不要憑記憶猜模型名。**

## 1. 指揮官不下場原則

主對話（指揮官）只做五件事：**任務定義、風險判斷、最終決策、結論彙整、使用者溝通**。

以下一律派 subagent 或拆成明確子任務：

- 大量讀取（讀超過 ~5 個檔案或超過 ~1000 行）
- 掃 repo / 搜尋符號 / 找出所有呼叫點
- 批次改檔（同一 pattern 改 3 個以上位置）
- 批次驗證（跑測試矩陣、對多個輸出檔做一致性檢查）
- 研究類（查外部文件、比較方案）

理由（寫給弱模型）：主對話的 context 是最貴的資源。你在主對話裡讀進的每個檔案，會佔用之後所有輪次的注意力。派工讓髒活發生在可拋棄的 context 裡，只有結論回到主對話。

**例外**：單檔小改（< 50 行 diff）、需要即時與使用者往返的探索——自己做比派工便宜。

## 2. 派工三件套

每次派工的 prompt 必須包含三件套，缺一不派：

1. **目標與動機**：做什麼 + 為什麼（讓 subagent 能在邊界情況自行做對取捨）
2. **驗收條件**：可判定的完成標準（測試綠、輸出檔存在且含某欄位、報告涵蓋某清單）
3. **回報格式**：subagent 最後一則訊息的結構

通用模板：

```text
## Task
（一句話目標）

## Why
（動機與上游脈絡，2-3 句）

## Scope
- In: （要碰的檔案/目錄）
- Out: （明確不准碰的東西；governance 任務必列 B 文件 hard constraints 相關項）

## Acceptance
- [ ] （可判定條件 1）
- [ ] （可判定條件 2）
- [ ] pytest 全綠（有改 code 時必列）

## Report format
最後訊息包含：結論（3 句內）/ 改動檔案清單 / 驗收逐條打勾 / 未解決事項
```

任務別的具體模板見 E 文件。

## 3. model / effort 指定規則

| 任務 | 等級 |
| --- | --- |
| 跑測試、收集輸出、格式轉換、照既有 pattern 複製 | `low-cost` |
| 照 J/K spec 實作 validator 規則、加測試、修明確 bug | `standard-coding` |
| 修改 governance 規則語意、設計新 workflow、處理模糊需求 | `high-reasoning`（若環境無，則 standard-coding + 人工確認） |
| Pydantic v1→v2 遷移這類機械大批量 | `standard-coding` 先解出一個檔的 pattern → `low-cost` 批次套用 |
| 驗收 / read-back / 對抗審查 | `fresh-context-reviewer`（重點是 context 新鮮，等級可以低） |

## 4. 升降級路徑（硬規則）

1. **`low-cost` 錯一次 → 直接升級** `standard-coding`。不要讓便宜模型重試，重試成本 > 升級成本。
2. **`standard-coding` 同一子任務連錯兩次 → 帶完整失敗軌跡升級** `high-reasoning`。失敗軌跡 = 兩次的 prompt、輸出 diff、錯誤訊息。不帶軌跡的升級等於重來。
3. **`high-reasoning` 解出模式後 → 降回便宜模型批次套用**。強模型的產出物應該是「可複製的 pattern + 一個已驗證的範例」，不是親手做完全部。
4. **同一件事最多重試兩輪**（不論等級）。第三次仍失敗 → 停止，向使用者回報：做了什麼、失敗軌跡、卡在哪、建議的下一步選項。
5. **無 `high-reasoning` 可用時**：把任務拆小到 `standard-coding` 能處理，或直接標註「需人工/強模型」擱置。不要硬做。

## 5. 驗證不自驗（硬規則）

原作者（包含模型自己）不得是自己工作的唯一驗收者。

| 產出類型 | 驗收方式 |
| --- | --- |
| 文件 | `fresh-context-reviewer` 做 read-back：只給文件本身（不給撰寫過程），要求覆述規則並回答 3 個場景題；答錯處即文件缺陷 |
| 程式碼 | 測試或實跑。「我讀過 diff 覺得對」不算驗收。新功能必須有新測試；bug fix 必須有先紅後綠的測試 |
| 高風險判斷（governance 規則變更、enum 變更、apply 邏輯） | `second-opinion` 或人工審核，二者至少其一。**restricted / pending / governance 相關變更，不得只靠原作者自驗，無例外** |
| 資料輸出（preview、報告） | 抽樣對照：隨機抽 3–5 筆與來源比對，加上總數 sanity check（計數對不對得上） |

## 6. 何時必須停下來（不派工、不重試、不硬做）

- 任務要求違反 B 文件 hard constraints → 停止，回報衝突。
- 需要真實 production data 才能繼續 → 停止，說明缺什麼。
- 判斷屬於「商業語境 / 公關風險 / 品味」（例如：這個 restricted_note 的措辭算不算允許新聞稿使用）→ 這不是 harness 能補足的，交人工。判準見 D 文件 rubric 3。
- 使用者的指示與制度文件衝突 → 指出衝突，請使用者裁決，用使用者的裁決結果更新文件（走 F 流程）。
